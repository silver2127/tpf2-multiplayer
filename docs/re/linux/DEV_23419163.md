# dev 23419163 (release 0.6): Linux evidence

Read-only analysis of Steam Linux build 35924; `readelf -n` confirms build-id
`3a0e156390b0e6f1e372051c24802c8493ae454a`. The ELF was read with objdump,
capstone and the `~/tpf2-re/linux` exports, never executed. Addresses are
PIE-relative (first PT_LOAD maps file offset = vaddr).

## roadentries (f6195dd): installed

### Windows contract

A post-call hook right after `call EdgeUseManager::Add` (0x2115f80) inside
`AddToEdgeUseManager` (0xa64390) re-sorts that edge's 20-byte entries by vehicle
Name (train-order comparator, then entity id). Refuses bad spans and more than
512 entries. Only this caller is hooked; PersonMoveSystem::EntityAdded
(0xa58f70) and TramMoveSystem (0xac27b0) also call Add and are left alone.

### Linux anchors

Signature exports (`funcsig.csv`) give one-to-one counterparts:

| --- | --- | --- |
| a64390 AddToEdgeUseManager | `16c4780` (302 bytes) | `{anonymous}::AddToEdgeUseManager(const ecs::Engine*, ecs::Entity, transport::EdgeUseManager&, CVec2f)`, RoadVehicleMoveSystem.cpp |
| a64be0 RoadVehicleMoveSystem::EntityAdded | `16c7900`, calls it at `16c7e13` | RoadVehicleMoveSystem.cpp |

`objdump` finds exactly these three `call 2e58f70` sites in the whole image.

### ABI of Add (from `2e58f70` and its caller)

At `16c482f..16c484a` the caller loads a 12-byte record of the vehicle's path
component: `mov rsi,[rax]` (EdgeId, 8 bytes: two int32), `mov edx,[rax+8]`
(forward), `mov ecx,[rbp-0x44]` (entity), `mov r8d,r13d` (component index),
`mov rdi,rbx` (the EdgeUseManager reference), xmm0 still holds the CVec2f
bounds reloaded at `16c47ec`. `16c484a: e8 21 47 79 01` calls `2e58f70`; the
function then only checks the canary and returns. Throughout, r12 holds the
ecs::Engine (`16c4797 mov r12,rdi`; used at `16c47c9` for the type map at +0x48
and `16c47dd` for pools at +0x80, the layout the tested Linux Name reader uses).

Add itself: `2e58f75 movq rax,xmm0; shr rax,32` (front) and `movd [rbp-0xec],xmm0`
(back), `mov r13d,ecx` (entity), `[rbp-0xe0]=rsi` (EdgeId; +0 index, +4 slot),
`[rbp-0xf0]=r8d`, `[rbp-0xd8]=edx` (stored as a byte). Its inlined lookup at
`2e59028..2e590a4`: int32 index vector at manager+0x30/+0x38, groups at
+0x48 (stride 72, `lea rdx,[rax+rax*8]; lea r15,[rax+rdx*8]`), a vector of
32-byte EdgeData per group (`sar r14,5`), EdgeData+0 the edge length asserted
> 0. The push_back at `2e59441..2e5946a` builds entity, component, back, front
(`movups` 16 bytes) and the forward byte, advances by 0x14 and stores the new
end at EdgeData+0x10 against capacity +0x18. So entries are libstdc++
`vector<20-byte entry>` at EdgeData+8, the same record as Windows'
`RoadUseEntry`; the group end at manager+0x50 is used by Add's grow path
(`2e591c0`). This matches the layout recorded for GetEdgeDataPtr in
[DEV_6CB03915.md](DEV_6CB03915.md).

### Patch

`Tpf2mpRedirectCall(16c484a, 2e58f70, SliceRoadEntriesRelay)` rewrites only the
rel32 of that call to a near stub (`mov rax,imm64; jmp rax`). The relay is
`endbr64; mov r9,r12; jmp SliceRoadEntriesAdd`: Add has five integer arguments,
so r9 is free, and the tail jump keeps the return into AddToEdgeUseManager and
the entry stack alignment (rsp = 8 mod 16). `SliceRoadEntriesAdd(mgr, EdgeId,
forward, entity, comp, engine, CVec2f)` calls the original Add with the same
SysV arguments (the `{float,float}` struct is one SSE eightbyte = xmm0), then
reads the edge with guarded reads in Add's layout, reads Names with the
existing `SliceNameComponent` (type from TypeFind `9e3d50` with the Name type
info at `5a02600`, as shiporder/airorder do), insertion-sorts with
`TrainOrderNameCmp` then id, and writes the entries back only when the order
changed. An unreadable edge is left alone; a span that is not whole 20-byte
entries, more than 512 entries or an allocation failure is counted as refused
and left alone. Callee-saved registers are untouched by the relay.

Guards (`kRoadEntriesChecks` in `movement_checks.h`): all 302 bytes of
AddToEdgeUseManager, Add's first 147 bytes (argument saves), its lookup
`2e59028` (124 bytes) and push_back `2e59441` (46 bytes). The install also
requires the Name layout/accessor checks shared with ship/air order and that
the site is still `e8` to `2e58f70`. `roadentries=0` leaves the call alone; a
failed guard leaves it alone and multiplayer readiness false.
`tools/linux/verify_movement_elf.py` checks the four spans, that `16c484a`
is a call to `2e58f70` and that Add's push_back advances by 0x14.

## stationicon ctor/attach/EnginePtr (daca5b9, c4c1e86, 093dfff, 1fef2d5): not installed

New evidence, which resolves part of the entity/engine provenance gap recorded
in [DEV_D6DB920F.md](DEV_D6DB920F.md):

- The Linux station factory `1090250` (StationItem constructor counterpart;
  it loads the `StationItem` string `3f2b74a` and contains the eleven
  `::StationIcon` carrier branches) has exactly two callers: `1095972` in
  `UI::HudIconManager::DoStep` (`1093b30`) and `10920b5` in the unnamed
  `1092040` (424 bytes), the counterpart of the Windows cargo-state rebuild.
- Entry saves `rsi` (EnginePtr) at rbp-0xa8, `rdx`, `rcx`, `r8` and
  `r9d` as a DWORD at rbp-0xc4. `10902c8` calls `146f0a0(&EnginePtr)`, whose
  body is `call 1477120; mov rax,[rax+0x28]; ret` — the Windows
  `0x8b9e60` accessor shape — and `10902cd..10902e4` pass that result with
  `rsi=&[rbp-0xc4]` into `109a8f0`. So on Linux the entity is the 32-bit r9d
  argument and the engine is derived from rsi, both at constructor entry.

Not ported, because what they feed is still missing on Linux: there is no
native tint-class application (TintApplyClass / owner class relay across the
eleven station carrier branches and the inlined depot path), no verified
non-asserting PlayerOwned owner lookup at these sites, and no post-attach
restyle target identified in DoStep (the Windows `call 0x224a920` after the
constructor; on Linux `1095977..10959ab` wraps the result into a 0x440-byte
object through `306fd80`, which was not traced to the HUD-layer attach). A
constructor hook without the class application would change nothing visible.

## Frozen join / resync title-menu (f94d8c0, bb0a988, ebcbed7)

The Linux lobby parses the roster's `join_freeze` and, when true, takes no
hot-join save (`lobby_linux.cpp` ApplyRoster), as `menu_hook.cpp` does.
The `NativeIo::Loading()` title-menu exception has no Linux counterpart to
port: Linux has no native resync load controller (see DEV_6CB03915.md), so
`CreatePage(2)` is only reached by a real return to the menu. The Linux
netpunch child is started without `--sync-runtime-dir`, so `host_has_world()`
and frozen joins are inactive on a Linux host, and a Linux joiner advertises
recovery 0, which makes a Windows host fall back to its hot-join save.
