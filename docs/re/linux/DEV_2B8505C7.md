## Source comparison and native decision

The three incoming files add `TightBudgetMB` and use it in the terrain and
material workers, with ctypes coverage. No engine hook, instruction bytes,
address, layout, calling convention or allocation ownership changes.

Windows samples `MEMORYSTATUSEX.ullAvailPageFile`. While its sticky commit-tight
flag holds, the new target is resident bytes minus the deficit to the commit
threshold plus 1 GiB, rounded up to MiB and bounded by the previous target and
a 256 MiB floor. Loading or free commit below half the threshold retains that
floor. Both Windows paths and their tests are retained unchanged.

Native `bigmap/linux/terrain_pager.h::Policy` calls
`linux_memory::TerrainTarget` once per second in automatic mode, supplying
current resident/live bytes and `/proc/meminfo` MemAvailable. That function
already computes min(live, cap, max(0, resident + available - reserve)).
Reserve is physical RAM/7 bounded to 2..12 GiB; cap is RAM/4 bounded to
4..8 GiB. It never subtracts a shortfall from yesterday's target and has no
flat 256 MiB pressure clamp. Explicit configured budgets remain fixed.

Keep that native policy. Do not substitute Linux Committed_AS for Windows
free commit: the native pager keeps the arena mapped and uses
`madvise(MADV_DONTNEED)` after encoding into a separate anonymous allocation.
There is no proved one-for-one release of Linux commit accounting, and the
policy is intended to reserve physical memory. The Windows sticky flag,
load-state controller, emergency floor and material pager do not exist in
this native backend. Its pressure target can be zero and it can grow again
when MemAvailable recovers; this is not claimed to reproduce Windows' full
controller. Existing material/small-pager limitations remain as documented
in [the original integration](DEV_8C3C02A5.md) and
[Big Maps port record](../../../bigmap/docs/linux/PORT.md).

## Evidence

Added deterministic cases to the existing native pager test: 2724 MiB resident
and 1536 MiB shortfall keeps 1188 MiB; unchanged repeated samples keep the same
target; partial/full reclamation with corresponding available-memory recovery
also keeps it; reserve boundary, one-byte shortfall and deficit larger than
resident memory are covered. These run before the userfaultfd availability
check. Reclaim inputs are a synthetic accounting model, not game measurements;
compressed blobs and unrelated allocations affect real MemAvailable.

The existing verifier read the actual lab ELF and passed its build-id and all
30 patch-site byte checks. No new site or ABI requires disassembly or live gdb
proof for this source-only policy comparison. No game was launched, and no
loaded-map stutter or memory-performance result is claimed.
