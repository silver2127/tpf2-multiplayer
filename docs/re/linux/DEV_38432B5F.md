# dev 38432b5f: paused GameTime and loading progress

Static inspection of Linux Steam build 35924, GNU build-id
`3a0e156390b0e6f1e372051c24802c8493ae454a`. The game was read, never executed.
Addresses below are ELF virtual addresses relative to the PIE image base.

## Paused tick

Anchor: the existing [save/thread map](SAVE_NONBLOCKING.md) identifies
`GameSim::Step` at `0xa61250`. Fresh objdump inspection of its complete body
(`0xa61250..0xa618ed`) establishes the two paths. At `0xa616b9` it calls the
already identified `CGameTime::GetSpeed` at `0xc0dc30`, tests eax, then jumps
at `0xa616c0` to `0xa61850` when speed is zero.

| Site | Bytes / meaning |
|---|---|
| `0xa61850` | `48 8b 43 08 31 d2 8b b0 10 02 00 00 48 8b 78 28 e8 db bf d3 00` |
| `0xa61860` | paused call `e8 db bf d3 00` resolves to `0x179d840` |
| `0xa617c3` | `48 8b 43 08 ba 01 00 00 00 8b b0 10 02 00 00 48 8b 78 28 e8 65 c0 d3 00` |
| `0xa617d6` | running call, same target, edx=1; retained unchanged |
| `0x179d86a` | `89 95 0c ff ff ff`: preserves edx at rbp-0xf4 |
| `0x179dac3` | `48 8b 85 70 ff ff ff 83 40 30 01 80 bd 0c ff ff ff 00 0f 85 a5 00 00 00` |
| `0x179db80` | `83 40 34 01 e9 52 ff ff ff`: conditional second increment, rejoins at `0x179dadb` |

The advance ABI is SysV: rdi=ECS engine from `[world+0x28]`, esi=time entity
from `[world+0x210]`, edx=stepped boolean. The counter update adds one to
component+0x30 unconditionally, tests the saved boolean, and only then adds
one to +0x34. No MSVC register assignment was reused. The RTTI address used
by the component lookup is `0x5a02380`, also used at the beginning of Step.
The existing train-order map's counter accessor `0xc0cf10` independently
ends in `mov eax,[rax+0x30]` (`8b 40 30`, at `0xc0cf26`).

Replace only the five bytes at `0xa61860` with `0f 1f 44 00 00`. Six complete
instruction spans, including speed dispatch, both argument setups/calls and
both increments, are checked before writing. The build-id and SliceRead
backend gates are inherited from slice initialization. The common
`Tpf2mpCodeWriteSelf` writer checks its readback; a failed guard writes nothing.
`pausedtick=0` in the existing root/data menu flags disables this change.
No trampoline, foreign call, component layout modification or new hook ABI
is needed. The same-save initial counter offset is retained, as on Windows.

`verify_dev_38432b5f_elf.py` compares the checked-in bytes with PT_LOAD bytes,
checks complete instruction boundaries, resolves both calls, distinguishes
their boolean values, and checks that no direct branch in Step targets the
interior of the removed call. The synthetic native test mutates one guard,
checks refusal without changing the call, restores it, applies the NOP to a
private fixture, and checks that the running path remains unchanged.

## Loading percentage

Anchor: `xrefs.csv` locates the assertion `m_progressBar` in `0x115cfe0` at
`0x115d162`. This is the completion lambda with the same MenuUI.cpp line
`0xe65` as Windows. It loads the menu from the closure, reads menu+0x498,
asserts non-null, and calls `0x30ea860` at `0x115d027`. That function copies a
libstdc++ shared_ptr: rdi is the return slot, rsi is the progress bar;
`[rsi+0x440]` is the monitor and `[rsi+0x448]` its control block. The completion
lambda calls the monitor's vtable+0x18 getter and constructs a SubProgressMonitor
for `1-current` at `0x115d050`, then calls the already identified StartGame
`0x115b000`. The offsets happen to agree with Windows, but were derived here.

RTTI derivation from `.rela.dyn`:

- name `N2UI15ProgressMonitorE` at `0x4f368c0`;
- typeinfo `0x5a33820` points to that name at +8;
- vtable address point **`0x59d8c60`**, typeinfo reference at `0x59d8c58`;
- two destructor slots: `0x30ebcd0`, `0x30ebe00`;
- SetProgress at +0x10: `0x30ebd30`, `movd eax,xmm0; mov [rdi+8],eax; mfence`;
- GetProgress at +0x18: `0x30ebd10`, reads `[rdi+8]` and returns float in xmm0.

The extra destructor slot is the Itanium ABI difference from the Windows
vtable. Runtime installation verifies four instruction spans (completion
lookup, shared_ptr accessor, setter, complete getter) and all four relocated
vtable entries. Exact bytes live in `progress_checks_linux.h` and the ELF
verifier checks them, the RTTI name and relocations.

The already byte-verified CreatePage detour captures the CMenuUI pointer.
Polling uses `process_vm_readv` for every pointer/float read, checks the monitor
vtable and 0..1 range (rejecting NaN), and returns unavailable on any failure.
There is no direct foreign call, C++ object copy, or lifetime-sensitive
shared_ptr operation. Unreadable progress falls back to the existing text.
100% is never reported numerically: it can be the preceding load's retained
value. An in-world arm waits for an observed load or 20 seconds before reading
the script's status. Linux's previous lack of automatic in-world client load
remains; manual host loads and title-menu auto-load use the new watch.

## Other native behavior

The companies gate reads `cm=companies` in the current instance's status file,
then falls back to `mp_company_cfg.txt`, under its existing two-second mutex
cache. No new engine address is involved. Tests cover sim-created companies,
co-op, another instance and the lobby fallback.

The existing verified CreatePage/page-2 and CGameUI frame notifications identify
return to title. Only a previously observed world plus a running lobby triggers
Leave. Linux Leave queues child teardown on the lobby worker; CreatePage never
waits for the child. Tests distinguish a waiting joiner, page-16 world switch,
actual return to title and repeated page-2 notifications. No new patch site.

Static and synthetic tests establish mapping and refusal behavior, not live
UI timing or cross-platform gameplay compatibility.
