# Adaptive Steam send rate: dev 0620342e

This commit changes Steam configuration/controller logic and mod-owned menu
widgets. It introduces no TransportFever2.exe hook, game address, byte pattern,
structure offset or MSVC STL boundary. Existing native menu drawing/input and
[Messages export mapping](DEV_1EB30002.md) are reused.

Read the actual lab TransportFever2 ELF notes: GNU build-id
3a0e156390b0e6f1e372051c24802c8493ae454a, build 35924.
Disassembled the lab libsteam_api.so export
SteamAPI_ISteamNetworkingUtils_SetConfigValue at library-relative 0x241f0:
48 8b 07 / 48 8b 80 80 00 00 00 / ff e0.
It loads the interface vtable from rdi and tail-jumps to slot +0x80.
The implementation resolves the export by name, never patches this address.
SysV arguments are interface/value/scope/object/type/value-pointer in
rdi/rsi/rdx/rcx/r8/r9; the C++ compiler provides the ABI.

The vendored steamnetworkingtypes.h defines SendRateMin=10, SendRateMax=11,
global scope=1 and int32 type=1. Existing status fields provide remote quality,
outgoing bytes/sec, pending bytes and unacked reliable bytes. These are typed
Valve ABI fields, not guessed game offsets. Fixtures exercise the actual native
adapter and configuration call arguments. The shared controller is plain C++,
with uint32_t monotonic milliseconds supplied by Linux's existing DWORD shim.

No new engine patch requires byte guards or entity/lifetime RE. Static API
evidence is saved in meta/live/steam-setconfig.txt and elf-notes.txt.
The lab launch was attempted with this build but failed before exec at the
bubblewrap uid map. No live ABI invocation, menu observation or real-peer
throughput is claimed. No speculative engine code was introduced.
