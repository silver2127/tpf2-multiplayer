# Steam transport integration plan (Steam as signalling, Steam Networking Messages as the relay fallback)

Status: plan, 2026-09-08. Winning design: "minimal-signaling", with the grafts and corrections from the three judge passes and the export-dump / header cross-check folded in. Facts marked (verified) were checked against the game's `steam_api64.dll` export table (dumped to `scratchpad/steam_exports.txt`, 1065 names), against Valve's headers and docs fetched this week, or against source this week.

## Executive summary

1. We gain: no code paste (a Steam overlay INVITE, or a friends-list Join Game on a password-locked lobby, carries the netpunch code inside a friends-only Steam lobby), and no inbound UDP 29471 requirement when the punch race fails (a Steam Networking Messages tunnel through Valve's relays takes over after 5 s).
2. We keep: `net.cpp`, the `netpunch/` Python stack (roster, chat, seal, NPF1 save transfer, mesh), the `lobby_in/out.jsonl` contract, the MSI file list and the autotest verdict scraping. Changes outside the menu DLL are bounded: ~150 lines of Python (via candidate, tunnel pacing, version handshake, stable slots), ~15 lines of `lockstep.lua` (`K.PROTO`, `hostgone=` freeze), one new ctl key the bridge already logs-and-ignores.
3. The one architectural decision: Steam is a signalling and relay layer under the existing lobby protocol, not a new data plane. The tunnel is a datagram NAT onto `lobby.py`'s existing NP1 socket, so every joiner still looks like a UDP source address to the host.
4. All new code lands in `tpf2_menu.dll` (`steam_glue.cpp`, `steam_tunnel.cpp`, ~150 lines in `menu_hook.cpp`). `tpf2_bridge_mp.dll` is untouched.
5. The flat API is resolved by `GetProcAddress` off the game's already-loaded `steam_api64.dll`; no SDK files are shipped, no app id of our own is needed. SDR P2P needs no backend of ours: Valve's SDR page says P2P needs only `CreateListenSocketP2P`/`ConnectP2P` (or the Messages equivalent) and "Steam will take care of everything else". Whether relay access is actually granted to app 1066780 is measured in M-S0, not assumed.
6. Callbacks ride the game's own `SteamAPI_RunCallbacks` pump; three hand-rolled `CCallbackBase` objects (overlay active, lobby invite accepted, rich-presence join), everything else polled or delivered through exported `SetGlobalCallback_*` function pointers. The tunnel handshake is symmetric so it never waits on the pump.
7. Players without Steam Friends access (a Steam exe without a Steam login, the Sandboxie rig, a future GOG port) keep today's code-paste flow; every Steam feature is gated on `steam_api64.dll` present, six accessors non-null, `GetAppID() == 1066780`, and `SteamAPI_ISteamUser_BLoggedOn` true. GOG itself is not a working path today (the menu hooks by RVA of Steam build 35924); it is a separate RVA-port item.
8. Every switch is default-off until M-S4: `steam=0`, `steam_probe=0`, `steam_via=0`, `steam_via_force=0`, `steam_fake_backend=0`, `steam_join_lobby=0`. The rig always forces `TPF2MP_STEAM=0` unless a Steam lane is requested.
9. One machine plus one account proves M-S0 and the read paths; the fake tunnel backend proves the NAT and the Python changes on the existing two-instance lobby rig; the laptop with a second TpF2 licence is needed only for invite acceptance and real SDR traffic.
10. About three to four focused weeks, one extra Transport Fever 2 licence for the laptop account.

Steamworks API calls are thread-safe in general (per-thread IPC pipes; SNS/SNM live in-process behind an internal lock), which is what the split relies on; the plan does not claim any per-interface documentation. Callbacks (331/333/337 and the two `SetGlobalCallback_*` pointers) arrive on the game's pump thread and only enqueue: each `Run` body copies exactly its struct size into a mutex-protected queue under `__try/__except` and returns; it never calls Steam. Self-id guard: `SG_HostLobby`, `SG_Join` and the tunnel refuse (log `[steam] peer id == own id, steam features off for this session`) when a lobby member or session peer has the same SteamID64 as `SG_SelfId64()`, so an online same-account Sandboxie box can never join our own lobby or open a tunnel to itself.

### Message framing

Two independent framings, neither changed:

- Line-based lockstep frames stay inside `net.cpp` packets inside `'g'` NP1 frames. The tunnel never parses them.
- Tunnel unit = one UDP datagram = one Steam Networking Message on channel 0. Sizes: `k_cbMaxSteamNetworkingSocketsMessageSizeSend` is 512 KiB; `k_cbSteamNetworkingSocketsMaxMessageNoFragment` is 1200 bytes. Every tunnel datagram is designed to fit one unfragmented message and is sent `UnreliableNoNagle | AutoRestartBrokenSession` (1|32): a `'g'` frame is a 1046-byte bridge packet plus NP1 and seal overhead (~1076 B); an NPF1 save chunk to a 127.0.0.2 target is 1180 B payload + 12 B NPF1 + 5 B NP1 + 0 seal = 1197 B. `lobby.py`'s receiver-driven ARQ is the only reliability layer, so Steam's reliable queue never fights the Python resend timer. A datagram above 1200 B should not occur (`GAME_RELAY_MAX = 1400` is above it but the bridge never fills it); if one does, it is logged once per session and sent `Reliable | NoNagle | AutoRestartBrokenSession` (8|1|32) rather than fragmented-unreliable.
- `k_EResultLimitExceeded` from `SendMessageToUser`: drop the datagram and count it, never spin. `SetConfigValue(k_ESteamNetworkingConfig_SendBufferSize = 9, Global, Int32)` raised once to 16 MiB at tunnel start (default is 512 KiB, which the 2048-chunk remote window would overflow; TIMP uses 96 MiB). Every 127.0.0.1/127.0.0.2 tunnel socket gets `SO_RCVBUF`/`SO_SNDBUF` of 8 MiB so `lobby.py`'s burst is not dropped by the default ~64 KB loopback receive buffer before Steam sees it.
- Pacing: `lobby.py` gains a per-target pacing class; targets under `127.0.0.2` use `SEND_BUDGET_TUNNEL = 24` datagrams per 2 ms pump and `RESEND_AFTER_TUNNEL = 2.0 s`, both exposed as cfg for stage 2 tuning; `fbegin` logs `budget=` and `fdone` logs `retransmit ratio`.
- Liveness: `SetConfigValue(k_ESteamNetworkingConfig_TimeoutConnected = 25)` to 20000 ms (default 10000) and the host's per-remote idle close at 30 s, so the lobby layer (`DROP_AFTER` 10 s, `HOST_GONE_AFTER` 12 s) is always the first to notice a dead peer and the only one that acts; an SDR re-route with `AutoRestartBrokenSession` is then invisible to the roster. `[tunnel] session restarted` is logged on the first message after a Broken state so the two clocks can be compared in stage 2. Idle sessions time out silently in Steam, so the tunnel sends a 1-byte channel-0 keepalive when a session has been idle >5 s (lobby.py's ping/roster traffic normally covers this; pre-START and paused states may not). `GetSessionConnectionInfo` (verified export) is polled every second into two zeroed 2048-byte buffers; only `m_eState` (first int32 after the 136-byte identity) and `m_nPing` (start of the realtime struct) and `m_eEndReason`/`m_szEndDebug` on failure are read, everything else is opaque. Log line `[tunnel] <id4> state=<n> transport=<kind> ping=<ms>`.
- ICE policy: `SetConfigValue(k_ESteamNetworkingConfig_P2P_Transport_ICE_Enable = 104, Global, Int32)` is set to `All` (0x7fffffff) only when the lobby has a password or the user opts in (`steam_ice=1`), else `Relay` (1). Public ICE reveals the IP to the peer exactly as today's direct UDP does; relay-only hides it at the cost of relay throughput. The default `-1` ("use user defaults") is never left in place, so the behaviour is ours to document.

### Identity model

- `lobby.py` still keys peers by UDP source address. A tunnelled joiner appears to the host as `127.0.0.2:<pN>` (one loopback socket per accepted SteamID; Windows delivers `127.0.0.2:pN -> 127.0.0.1:29471` because the host socket binds `0.0.0.0`, verified). The host tunnel logs `[tunnel] map 127.0.0.2:<pN> -> steam ...<last 4 digits>` on the first session message; that line is the future hook for binding origin letters to authenticated SteamIDs without touching Lua now.
- Letters come from stable per-peer slots assigned by the host at join time and shipped in the roster (M-S1), no longer from sorted position.
- SteamID64 replaces `ip:port` only in two places: the lobby driver (who is the host, who is a member) and the tunnel (who may open a session). Identities are built and read only through `SteamAPI_SteamNetworkingIdentity_SetSteamID64 / GetSteamID64 / ToString / Clear` (verified exports); we never touch the 136-byte union.
- Admission: the host opens sessions itself, from its own 1 s membership poll, by sending hello to every lobby member it has no session with (a send is also the accept for a pending request). The fast-path `SteamNetworkingMessagesSessionRequest_t` callback only queues the identity; SteamThread re-reads `GetNumLobbyMembers / GetLobbyMemberByIndex` (local cached data, cheap) before `AcceptSessionWithUser`. An unknown identity is ignored, never refused permanently; it is re-evaluated on the next request or poll, so a freshly joined member's first hello is never lost to a stale cache.
- Logging: SteamID64 redacted to the last 4 digits in `tpf2_menu.log` and therefore in the `--forward-log` merged `lobby_peers.log`, matching `RedactIp`.

### Security model changes

What `seal.py` provides today and keeps providing: encryption and integrity of every control and `'g'` frame under a key derived from the 12-byte code secret plus password; the code is the credential. This does not change. Over the tunnel the same sealed frames are carried, so a compromised relay sees ciphertext.

What Steam adds: per-session encryption and an authenticated remote SteamID on every message (additive), plus lobby-membership admission at the tunnel (a SteamID that is not in our friends-only lobby cannot open a session, before any NP1 byte is seen).

What changes in exposure, and must be written into `docs/SECURITY.md`:
- The code now sits in Steam lobby metadata. Anyone who obtains the 64-bit lobby id can `RequestLobbyData` (verified export) and read `np_code`, for a FriendsOnly lobby exactly as for a Private one. Without a password the code embeds the host's public IP. Mitigation: with `has_password=1` the published code is the locked form and carries no readable address; the UI hint on INVITE says so. The real gate is unchanged: the password-locked code, `seal.py`, and the tunnel's membership check.
- Who can obtain the lobby id: invitees (overlay dialog), anyone the host pastes the decimal id to, and, only when `has_password=1`, every Steam friend via rich-presence `connect` (`GetFriendGamePlayed`). Without a password no `connect` key is set, so an uninvited friend sees only the status string.
- Version and protocol are checked on both paths: Steam lobby data at `JoinLobby`, and the `join` message on the wire (`ver`/`proto`; host `reject` with "version: host 0.3.2/p2, you 0.3.1/p1"), so a code-paste pairing of mismatched builds is refused, not silently desynced.
- Password stays, unchanged role: it locks the code and derives the seal key. On the joiner it is typed into the existing field before JOIN; `StartLobby(1)` passes it as `--password`.
- Persona names never enter roster, lobby data or logs. No public lobby, no lobby browser: the friends-only threat model is unchanged.
- Save receiver: finding 1 of the (untracked) audit is closed by `lobby.py:229-248, :1158-1163, :1206-1209, :1169-1174`, verified 2026-09-08; `SECURITY.md` gets a "Save receiver" paragraph saying so, since the tunnel makes hosts reachable through NATs they could not cross before.

## Callback dispatch decision

Ride the game's `SteamAPI_RunCallbacks` pump by default; do not use `SteamAPI_ManualDispatch_*`. The exe imports `SteamAPI_RegisterCallback` and `SteamAPI_RunCallbacks` statically (verified), so the game owns the pump and its `CCallback` objects (Workshop, overlay, cloud). `SteamAPI_ManualDispatch_Init` must be called after `SteamAPI_Init` (header), and ManualDispatch is a process-global mode switch on the shared `steam_api64.dll`; every binding that uses it (Steamworks.NET, Facepunch, steamworks-rs) treats it as exclusive with `SteamAPI_RunCallbacks`, and the game owns the pump, so we do not enable it. Valve documents `SteamAPI_RunCallbacks` as safe to call from multiple threads, with the callbacks then running on the caller's thread; the real hazard of a second pump is the game's own handlers executing on our thread, so we do not pump unless the M-S0 measurement forces the contingency below.

Consequences designed around: (a) Three true callback registrations, one static-storage `CCallbackBase`-derived object per id (a `CCallbackBase` has one `m_iCallback`, so one object cannot serve two ids): `GameOverlayActivated_t` (331, 1 byte, only the first byte is read even if a newer client delivers a larger struct), `GameLobbyJoinRequested_t` (333, `{CSteamID lobby, CSteamID friend}` = 16 B), `GameRichPresenceJoinRequested_t` (337, `{CSteamID friend, char rgchConnect[256]}` = 264 B). Each returns its own size from `GetCallbackSizeBytes` and copies exactly that many bytes. Layout `CCallbackBase {vptr; uint8 m_nCallbackFlags = 0; int m_iCallback}`, MSVC x64 vtable order `{Run(void*, bool, SteamAPICall_t), Run(void*), GetCallbackSizeBytes()}` (MSVC lays adjacent overloads out in reverse; confirmed by compiling a replica with the repo's MSVC 14.44 and calling each slot; Steamworks.NET's `CCallbackBaseVTable` does the same swap on Windows). All three are `SteamAPI_UnregisterCallback`ed in `SG_Stop` from `TeardownLobby`; a registered object whose vtable lives in an unloaded module is never left behind, and no Steam call is made after `DLL_PROCESS_DETACH` (the exe imports `SteamAPI_Shutdown`, which may already have run). (b) Session request/failed for the tunnel use the exported `SteamAPI_ISteamNetworkingUtils_SetGlobalCallback_MessagesSessionRequest` and `_MessagesSessionFailed` (verified) rather than raw config ids; if raw ids are ever needed they are 204 and 205 (202 is `Callback_AuthStatusChanged`, 203 is `Callback_RelayNetworkStatusChanged`). The GNS header says `ISteamNetworkingSockets::RunCallbacks` is not needed when using Steam's dispatch, confirming these ride the game's pump. Because `SendMessageToUser` implicitly creates a session on the sender's side only, and the receiver must accept (via callback) or itself send to that peer, the handshake is symmetric: the host sends hello to every member it has no session with on its 1 s poll (that send is the accept), the joiner sends hello every 1 s until it receives the host's hello. The callback accept is a fast path, not a dependency. (c) Everything else is polled from SteamThread: `IsAPICallCompleted / GetAPICallResult` for `LobbyCreated_t` (513, `{EResult, uint64}` = 16 B) and `LobbyEnter_t` (504, 24 B, success = `m_EChatRoomEnterResponse == 1`) with `iCallbackExpected` and a size check, `GetLobbyData`, membership, `GetSessionConnectionInfo`, `GetRelayNetworkStatus`. (d) Launch-from-invite while the game is not running needs no callback: Steam appends `+connect_lobby <id64>` to the OS command line, so Init parses `GetCommandLineW()`; `SteamAPI_ISteamApps_GetLaunchCommandLine` (verified export) is also queried but only returns the string when the app owner enabled "Use launch command line", which we do not control. (e) M-S0 measures the pump cadence and thread with an IAT counter on the exe's `SteamAPI_RunCallbacks` import (title menu, during load, in-game at speed 4, recorded twice). Contingency, written into M-S0/M-S2: if the in-game cadence is 0 for more than 2 s, either (i) accept that in-game invites are delivered only when the player returns to the main menu and document it, or (ii) pump `SteamAPI_RunCallbacks` from SteamThread only while the panel is open on main-menu page 2 and the game's own count has been 0 for 2 s. Optionally M-S0 also measures whether `SteamAPI_ISteamNetworkingSockets_RunCallbacks` (exported) called from TunnelThread delivers the session callbacks on our thread.
