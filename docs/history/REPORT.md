# TransportFever2.exe — Reverse-Engineering Recon Report
### Feasibility groundwork for a hypothetical multiplayer patch

Target: `TransportFever2.exe` (Steam build, exe dated Jun 21 2026)
Analyst pass: static strings/RTTI survey only — no disassembly yet. Read-only.
Generated by `extract.py` in this folder. All offsets refer to file offsets in the exe.

---

## 1. Executive summary

- **There is no multiplayer code in the engine to unlock.** Exhaustive string and
  RTTI scans for `multiplayer`, `netcode`, `lockstep`, `replication`, `desync`,
  `lobby`, `raknet`, `steamnetworking`, `replay` return **zero hits**. The only
  networking-adjacent imports (`WS2_32`, `WINHTTP`) serve Steam workshop /
  mod.io / crash reporting. Any MP would be built **from zero** and grafted on.
- **The engine has a clean, central command queue — the ideal hook point.**
  All player actions and all Lua `api.cmd.sendCommand()` calls converge on one
  class: `CommandList` (`src\Game\command\CommandList.cpp`, plus
  `apply_command.cpp` / `make_command.cpp`). RTTI shows
  `CommandList::Add` broadcasting `const std::vector<Command>&` over a
  boost::signals2 signal, and `CommandList::Swap(std::vector<Command>&)` —
  a classic double-buffered command queue. Hook two functions and you observe
  (and can inject) every state-changing action in the game.
- **The binary is unusually RE-friendly** for a shipped game: no packer, no
  anti-tamper, intact RTTI (2,609 class names), 731 assertion strings leaking
  full CI source paths and expressions, embedded Lua 5.2.2 with sol2 bindings
  whose registration names are plain strings.
- **Determinism is the open research risk** (see §6). The sim is a
  multithreaded ECS; nothing in the binary suggests it was built to be
  bit-deterministic across machines.

Verdict: a lockstep-style MP patch is *technically* approachable via the
`CommandList` hook, but remains a months-scale project with a real chance of
dying on sim determinism. This report gives the map; disassembly is next.

## 5. The command interface — the hook point

### 5.1 What the strings show

`SetupCommandInterface` (61 occurrences = heavily-inlined sol2 registration
function) registers the Lua `api.cmd` table. From the rodata window around
`sendCommand` (offset `0x314d5a8`, full dump in `lua_api_windows.txt`), the
registered command factories include:

```
bookJournalEntry   buildProposal      connectTownsAndIndustries
createLine         createTowns        deleteLine
developTown        instantlyUpdateTownCargoNeeds
removeTown         replaceTerrain     reverseVehicle
sellVehicle        sendScriptEvent    setAnimalState
setCalendarSpeed   setColor           setDate
setGameSpeed       setName            setVehicleManualDeparture
setTownInfo        setUserStopped     setVehicleTargetMaintenanceState
setVehicleShouldDepart               spawnAnimal
updateLine         setSimBuildingManualDevelopment
setSimBuildingClosureTimeStamp       buyVehicle   ...
```

plus the registration metadata pattern `command`, `callback[Result, Bool]`,
`context`, `ignoreErrors` — i.e. every command is a typed struct with a
result callback, marshalled through sol2.

Sibling setup functions map the whole scripting surface:
`SetupCoreInterface`, `SetupUtilInterface`, `SetupResourcesInterface`,
`SetupGuiInterfaceWith{,out}GameUI`, `SetupLegacyCommandInterface`.

### 5.2 The queue mechanics (from RTTI)

```
void CommandList::Swap(std::vector<Command>&)
CommandList::Add::<lambda>::operator()(const boost::signals2::connection&,
                                       const std::vector<Command>&)
```

`CommandList` accumulates `Command` structs; per frame/tick the buffer is
swapped out and applied by `apply_command.cpp`. **UI-originated and
Lua-originated actions use this same pipe** — that is the single choke point
an MP patch needs.

### 5.3 Lockstep hook design (what a patch would do)

1. **Observe:** hook `CommandList::Add` (or the signal) → serialize every
   `Command` (type tag + payload) with the local tick number.
2. **Transport:** send to peer(s); receive theirs. (enemeet/steam Datagram —
   note `steam_api64` is already loaded; Steam Datagram would be the
   path of least resistance.)
3. **Inject:** remote commands enter via the same `CommandList` (call the
   real `Add` from the hook) at the agreed future tick.
4. **Pace:** both instances must agree on sim tick boundaries — need the
   `GameSim`/`GameTime` update loop located and a fixed-timestep enforced.
5. **Gate input:** buffer local commands for tick N+latency instead of
   immediate application (classic input-delay lockstep).

Open questions only disassembly can answer:

- Exact `Command` struct layout & whether it's trivially serializable
  (union? polymorphic? raw pointers? — the legacy `cmd_interface.cpp`
  marshalling suggests structs are POD-ish, but verify).
- Whether command application order within a tick is stable.
- Where the per-tick boundary actually is (`GameSim.cpp`).
- Whether `api.cmd.make.*` and UI commands produce identical `Command`
  payloads for identical actions (needed for a script-driven test harness).

## 6. Determinism risk assessment

Lockstep lives or dies here. Concerns, in order of severity:

1. **Multithreaded ECS.** `ecs\*System` classes and job-style naming imply
   parallel system execution. If any system reads neighbor state in
   thread-scheduling-dependent order → divergence. Mitigation: patch the
   job scheduler to single-threaded (perf hit, correctness win).
2. **Floating point.** Same binary + same inputs on x86-64 SSE2 is usually
   stable; risk comes from `concurrency` (above) and any transcendental/
   fast-math paths. No `/fp:fast` evidence either way yet.
3. **RNG.** No shared sim RNG infrastructure is exposed; each system may
   carry its own state. Map seed UI exists, but in-game stochastic systems
   (town growth, industry) need their RNG states identified and seeded
   identically. Unsolved until disassembly.
4. **Hash iteration order.** `std::unordered_map<ecs::Entity,...>` appears
   in RTTI; iteration-order dependence is a classic desync source.

None of these are provably fatal — but each is a research task. Budget for a
"two instances on one LAN, checksum GameState each tick, bisect the first
divergence" phase before any real netcode.

## 7. Effort estimate (honest)

| Milestone | Scope | Realistic effort |
|---|---|---|
| M1 Ghidra project, RTTI/assert-guided symbol map | rename ~2.6k classes, map CommandList + GameSim | 2–4 wks |
| M2 DLL injector + CommandList tap (log all commands w/ tick) | proof of choke point | 1–2 wks |
| M3 Determinism harness: 2 local instances, same map+inputs, state checksum diff | the make-or-break | 4–12 wks (unknown unknowns) |
| M4 Lockstep transport (Steam Datagram), input delay, tick sync | netcode proper | 4–8 wks |
| M5 MP lobby UI, desync recovery (save-state resync via Serializer.cpp) | polish | 4+ wks |

M3 is the gate. If the sim can't be made deterministic, the fallback is
server-authoritative state-sync, which requires full ECS serialization
(`Serializer.cpp` helps but is save-file oriented, not per-tick) — roughly
double the effort with worse results.

## 9. Recommended next steps

1. Load exe in Ghidra with **pdb-free RTTI recovery** (use `rtti_classes.txt`
   to name vtables; use `asserts.txt` to name functions containing asserts —
   each assert string xref pins a function to a known source file:line role).
2. Find `SetupCommandInterface` via the string at `0x314d5a8` xref; walk its
   registration calls to recover the full `api.cmd.make.*` → C++ factory map.
3. Find `CommandList::Swap` callers → that call site is the per-tick apply
   point; the caller chain leads to `GameSim`'s main loop = tick boundary.
4. Write a minimal in-process DLL (LoadLibrary via a debugger first; Steam
   has no anti-cheat here) that detours `CommandList::Add` and logs every
   command + tick to a file. That artifact alone validates the whole design.
